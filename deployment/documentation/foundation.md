# Pi and Keycloak foundation

This slice runs Everything's API and real Pi SDK together, with Keycloak, PostgreSQL, the artifact service, and its image registry in separate Kubernetes pods behind the ingress. Teammates run on their saved provider, model, and effort; no provider or model is part of the deployment. The separate UI pod serves the React/Tailwind PWA, including one ongoing chat per teammate and the shared app library. Each teammate also has an always-running tools pod for file access and Bash; model sessions stay in Everything. fleetd runs inside Everything's container, connected to the cluster; delegating to it from teammates comes later (see [Fleet](#fleet)).

## Run it

Requirements: Node 24.11+, pnpm 10.34.6, Docker, kubectl, Helm, and Minikube with an ingress controller. The devcontainer provides all of them: its Node feature installs the pinned pnpm version during the image build, and its startup script starts Minikube, enables the metrics-server addon so `kubectl top` and k9s show CPU and memory, and installs Traefik as the default ingress controller (`.devcontainer/install-traefik.sh`). Package-manager setup does not need `sudo` or a post-create command; Node and pnpm use the feature's nvm-managed path. The deployment scripts only target the `minikube` context.

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm test
pnpm cluster:up
pnpm test:api          # Bruno API collection; forwards the ingress itself if needed
pnpm cluster:forward   # Serve the stack at http://localhost:8080 and apps at http://localhost:8081
```

The application's origin is `http://localhost:8080`: `cluster:forward` forwards the ingress controller there, on loopback only. The ingress routes `/` to the UI, `/v1` and `/health` to the API, and `/auth` to Keycloak, whose admin console is `/auth/admin`. `/health/live` and `/health/ready` are the only unauthenticated API routes. The artifact host is a second origin, `http://localhost:8081`; see [apps](#apps).

`cluster:up` creates the `everything` namespace, builds the UI, Everything, artifact service, registry, optimized Keycloak, and configured PostgreSQL images, imports them into Minikube, installs or upgrades the `everything` Helm release from `deployment/helm` with `values.dev.yaml` layered over `values.yaml`, and lets the Minikube node pull from the registry's hostname (see [apps](#apps)). Because the fixed development tags leave pod specs unchanged, it then restarts the Deployments in `rolloutWave` order. Existing databases and volumes are reused, and uninstalling the release keeps every persistent volume claim. `pnpm cluster:down` deletes the stack for a clean start: it uninstalls the release and deletes the release, artifact, build, and Fleet namespaces, including the database, Keycloak data, agent files, Pi state, artifact content, images, and every artifact's workload and disk. It asks for confirmation unless given `--yes`. Keycloak's startup realm import does not overwrite an existing realm; later realm changes require an explicit migration or an admin-console change.

## Deploy to a cluster

The same chart deploys to any Kubernetes cluster with an ingress controller, installed from a release (see [releases](#releases)). `deployment/helm/values.prod.yaml` overrides the development defaults: the image registry, the pull policy, the public origin and artifact origin, and the application, artifact, and registry hostnames. Its image tag is empty, so each chart version runs the images released with it. Copy it and replace its example hosts. The chart creates every Secret and the Keycloak realm itself; pass the passwords in a credentials values file kept out of Git, setting each key under `secrets` in `values.yaml`. A missing value fails the render and names the key. Create the release's namespace beforehand, labelled to admit the privileged Docker sidecar in Everything's pod. The chart creates the artifact, build, and Fleet namespaces, named after the release's namespace (`everything-artifacts`, `everything-builds`, and `everything-fleet` here), and keeps them when the release is uninstalled. Cluster-wide resources are named after it too, so several installations can share a cluster, each in its own namespace.

```sh
kubectl create namespace everything
kubectl label namespace everything pod-security.kubernetes.io/enforce=privileged
helm upgrade everything oci://ghcr.io/benjaminbenetti/everything/charts/everything \
  --version <version> --install --namespace everything \
  --values values.prod.yaml --values <credentials file>
```

The application's Ingress uses the cluster's default class unless `global.ingress.className` names one; the artifact host's Ingress reads the same settings from `global.artifactIngress`, and the registry's from `global.registryIngress`, whose host is `global.externalRegistryHostname`. TLS terminates at the cluster's ingress: configure the certificates there, for example through each Ingress's annotations for a certificate issuer and its `tlsSecretName` for the Secret the issuer fills. Nodes pull from the registry's hostname over HTTPS, so its certificate must be one they trust, and its Ingress must accept image uploads of any size, for example with ingress-nginx's `nginx.ingress.kubernetes.io/proxy-body-size: "0"` annotation. Services communicate over plain HTTP inside the cluster. `global.storageClassName` selects storage for every volume that does not name its own class.

### Releases

`.github/workflows/ci.yaml` runs the format check, `pnpm build`, and `pnpm test` on every push to `main` and every pull request. Pushing a semantic version tag publishes a release:

```sh
git tag v1.2.3
git push origin v1.2.3
```

`.github/workflows/release.yaml` first runs the same checks. It then builds every image the chart runs for `linux/amd64` and `linux/arm64`, each on a native runner, through Docker's reusable [GitHub Builder](https://github.com/docker/github-builder) workflow, which also signs the images' build provenance. It reads the images from the rendered chart and finds the workspace that builds each one from its `build:image` script, so a new service's image is released without changing the workflow; `pnpm build` fails if a chart image has no such workspace. Images are pushed to `ghcr.io/benjaminbenetti/everything/<image>`, tagged with the version without its `v` (`1.2.3`), plus `1.2` and `latest` for releases that are not prereleases. Once every image exists, the workflow packages the chart with the same version as its chart version and appVersion, pushes it to `oci://ghcr.io/benjaminbenetti/everything/charts/everything`, and creates a GitHub release with install instructions, the image list, generated change notes, and the packaged chart attached. Tags with a prerelease suffix, such as `v1.2.3-rc.1`, publish only the full version tag and mark the GitHub release as a prerelease. Tags with build metadata (`+...`) are rejected, because image and chart tags cannot carry it. The published chart leaves out `values.dev.yaml`.

GitHub creates each package the first time a release pushes it, and new packages can start out private. Nodes pull the images anonymously, because the chart configures no image pull secrets, so after the first release check each package's visibility on GitHub and make it public.

## Authentication and secrets

TLS is the cluster's responsibility. The ingress terminates it, Keycloak trusts the forwarded scheme and host (`KC_PROXY_HEADERS=xforwarded`), and in-cluster traffic, including the API's signing-key requests to Keycloak and both services' database connections, uses plain HTTP or PostgreSQL connections. PostgreSQL requires password authentication for every network connection.

The chart renders every credential into a Secret it owns (`database-credentials`, `keycloak-credentials`, `browser-auth`, `artifact-auth`, `app-provisioner-auth`, `registry-credentials`, the `keycloak-realm` import, and the registry's password file and push and pull credentials in `registry-credentials.yaml`), and containers read them as environment variables from those Secrets. The values come from a values file passed at install time. Development uses the committed `deployment/helm/values.dev.yaml`, whose fixed passwords are for a stack reachable only on the developer's machine: Keycloak's admin console login is `admin` / `admin`, and the seeded user is `owner` / `owner`. Every other environment passes its own credentials file, kept out of Git. Changing a database password after the first deployment does not rotate it inside PostgreSQL; run `pnpm cluster:down` to start over.

The chart renders the realm from `deployment/helm/files/keycloak/`. The production realm, `everything-realm.json`, contains only the provisioning service identity and no human users or test clients, and Keycloak fills in its `${EVERYTHING_WEB_CLIENT_SECRET}` placeholder from its environment. It disables self-registration and implicit flow and requires HTTPS for public requests (`sslRequired: external`), which the ingress provides. The confidential `everything-web` client allows the API’s password exchange; browser-facing redirect flows are disabled. The confidential `everything-artifact-client` client has only a service account, whose tokens carry the `everything-artifact` audience that the artifact service accepts. See [browser sessions](#browser-sessions) for transport policy and limitations. Create the single user in the admin console with the temporary bootstrap admin `admin`, then replace that admin with a permanent account.

Development seeds the realm: with `keycloakRealm.developmentSeed.enabled`, the chart merges `everything-realm.dev.json` over the production realm, filling in the passwords and client secrets from `values.dev.yaml`, the only file that enables it. The seed allows plain HTTP from local addresses (`sslRequired: external`), adds the user `owner`, and adds three confidential clients for verification: `everything-bruno`, `everything-outsider`, and `wrong-audience`. Their service-account tokens exercise the real Keycloak trust boundary without automating a person's password; they never ship in the production realm.

Every protected `/v1` request verifies an RS256 signature, issuer, audience, subject, timestamps, and Keycloak access-token type. Missing, invalid, expired, wrong-audience, and ID tokens are rejected. Session creation/restoration/logout are the explicitly public `/v1/session` routes. Agent access is scoped to the verified subject, including reads, message sends, interruption, and deletion; unknown and foreign agent IDs both return 404. No application role hierarchy is introduced.

Everything is a single-user application, so every namespace admits privileged pods: Fleet's Docker engine needs them, and so do the Docker-in-Docker devcontainers of Fleet's instances once the user turns on privileged workers. Containers still run without root, privilege escalation, or writable image filesystems unless their entry overrides that; the Docker sidecar in Everything's pod is the only privileged container the chart runs. Everything receives namespaced access to reconcile teammate StatefulSets and internal Services and observe their pods, the permissions Fleet needs in `everything-fleet`, and cluster-wide reads of nodes, storage, and runtime classes for Fleet. Tools pods receive no Kubernetes token. The artifact service receives Kubernetes API credentials: its service account may manage workloads, Services, Secrets, and disks in `everything-artifacts`, and Jobs in `everything-builds`. The current Minikube CNI does not enforce NetworkPolicy, so this slice does not claim network isolation between cluster pods.

## Code boundaries for review

The [repository map](../../README.md) follows deployment boundaries first. `services/ui` owns the frontend and its stateless static server, `services/everything` owns the API and Pi runtime, `services/artifact` owns artifact records, files, builds, workloads, and the artifact host, `services/registry` owns the image registry, `services/docker` owns the Docker engine image of Everything's sidecar, `services/keycloak` owns authentication configuration, and `services/postgres` owns database initialization and access configuration. Every service has its own `package.json` and `container/Dockerfile`. One Helm chart in `deployment/helm` deploys them all: generic templates render every entry under `services` in `values.yaml`, merged over `serviceDefaults`. Values shared by services live under `global` and are referenced from env values as templates. Images are `<registry>/<image>:<tag>`, combining the global registry and tag with each service's image name. Services list the path prefixes the Ingress routes to them, on the application's origin or, with `ingress.site: artifacts` or `ingress.site: registry`, the artifact host or the registry's hostname; `apiAccess` gives a service a ServiceAccount with namespaced Roles and `clusterApiAccess` a ClusterRole; `sidecars` run further containers in a service's pod as native sidecars, mounting the service's volumes by name; `sharedVolumes` declares volumes that several services mount, such as files one service writes and another serves.

### Adding a service

1. Create `services/<name>/` with a `package.json` whose `build:image` script builds `<image>:foundation`, and a `container/Dockerfile`.
2. Add an entry under `services` in `deployment/helm/values.yaml` with its image name, env, ports, probes, resources, volumes, and any `ingress` paths, and a `rolloutWave` after the services it needs at startup. Set `workload: StatefulSet` if it must never run as two copies, such as a database or a process holding in-memory state.

The entry inherits the default security contexts (a non-root user, a read-only image filesystem, no capabilities) and one replica. The chart renders its Deployment or StatefulSet, kept persistent volume claims, a Service for ports with a `servicePort`, and its Ingress paths; `values.schema.json` rejects misspelled or malformed settings, and `deployment/helm/ci/` holds example values that `pnpm build` renders. `pnpm cluster:up` derives the images to load and the restart order from the rendered chart (`deployment/script/stack-chart.sh`), so no script changes are needed.

Shared code is divided into focused workspaces, each following `src/<domain>/<type>/<file>`:

| Library | Responsibility and public exports |
| --- | --- |
| `lib/persistence` | `@everything/persistence/entity` supplies `BaseEntity` and `OwnedEntity`; `/repository` supplies the `Repository` interface, `OwnerScope`, and abstract `BaseRepository`. The base class implements scoped `getById`, `list`, and `delete` through TypeORM. `/schema` provides shared entity column mappings; `/transaction` provides serializable transactions with bounded conflict retries. EntitySchemas and migrations belong to the service. |
| `lib/security` | `@everything/security/identity` supplies the verified caller representation; `/token-verifier` supplies its authentication interface; `/keycloak` creates the JOSE verifier; `/fastify` supplies `requireAuthentication` and the `subject` accessor; `/browser` supplies same-origin cookie sessions; `/password-grant` supplies confidential Keycloak exchanges; `/client-credentials` supplies cached service-account tokens; `/session-cipher` supplies JOSE authenticated encryption. |
| `lib/agent-contracts` | Browser-safe agent representations, creation inputs, and field limits shared by the API and UI, without importing persistence or service code. |
| `lib/artifact-contracts` | Artifact representations, request inputs, and limits shared by the artifact service, Everything, and the UI. |
| `lib/ui` | React controls, accessible dialogs, brand artwork, and semantic tokens for all six themes. Public subpaths separate these responsibilities. |
| `lib/errors` | `@everything/errors` supplies `ApplicationError`, with a safe public message, stable code, and HTTP status; `/fastify` supplies the error handler that returns those failures and hides unexpected ones. Domain error codes stay in the service. |

Each service declares only the libraries it consumes. Libraries never depend on service code. Security owns its JOSE dependency; persistence provides the TypeORM base implementation while use cases depend on repository interfaces. The Fastify adapter is a separate security export with an optional Fastify peer dependency, so identity and token verification can also be consumed by other transports.

Everything's composition root calls `createKeycloakTokenVerifier({ issuer, audience, jwksUrl })` using its service configuration. Its protected HTTP scope calls `requireAuthentication(scope, verifier, sessionTokenResolver)`, which decorates the request identity and registers the fail-closed authentication hook in one step. Controllers use the shared `subject(request)` accessor. Future API services use the same identity, verification policy, and authentication failure response while supplying their own trust settings. Resource ownership and any future domain authorization remain service responsibilities. Keycloak owns user records. The API resolves cookie sessions and refreshes their server-held tokens; its authentication hook verifies tokens from either a session or an explicit bearer header. Explicit Authorization never falls back to a cookie.

Within Everything, code follows `services/everything/src/<domain>/<type>/<file>`. The paths below are relative to that source root. PostgreSQL owns database provisioning; the Everything service owns its application schema. No service imports another service's source code. Cross-service checks live in the separate `@everything/api-tests` workspace.

| Boundary | Responsibility |
| --- | --- |
| `agent/controller` | Expose agent definition operations; deletion goes through `AgentRemoval` so the runtime stops first. |
| `agent/service`, `agent/interface` | Agent use cases and contracts independent of PostgreSQL. |
| `agent/repository` | Mapped TypeORM operations for owner-scoped agent definitions. |
| `agent/schema`, `conversation/schema` | TypeORM EntitySchemas and TypeBox request schemas; length limits come from domain model constants. |
| `<domain>/error` | Each domain's `ApplicationError` subclasses, so every public error code is defined once. |
| `conversation/controller`, `conversation/service` | Visible chat, runtime status, interruption, and orderly deletion (`AgentRemoval`). |
| `conversation/interface`, `conversation/repository` | Visible-message persistence boundary and PostgreSQL adapter. |
| `runtime/interface`, `runtime/service` | Runtime contract and `AgentRuntime`, which owns one agent's turn and public status. |
| `runtime/adapter`, `runtime/tool`, `runtime/prompt` | The Pi SDK implementation, the `send_message` tool, and the main-agent prompt. |
| `workspace/interface`, `workspace/service` | Each agent's working directory on the shared agents volume, removed when the agent is deleted. |
| `session/controller`, `session/service`, `session/repository` | Same-origin login/logout, server-side refresh and revocation, capability-scoped encrypted persistence. |
| `health/controller`, `identity/controller` | Unauthenticated probes and `/v1/me`. |
| `http/` | Shared request-schema helpers, strict validation options, and public error mapping. |
| `application/bootstrap`, `application/factory` | The composition root (constructs adapters, injects dependencies, owns shutdown) and HTTP composition. |

`BaseRepository<TEntity, TScope, TRecord>` receives a TypeORM repository and typed listing options. Concrete repositories implement `scopeWhere` using mapped properties and relations, and `toEntity` to exclude persistence-only fields. Lookups and listings use TypeORM find operations; deletion verifies ownership and removes the record in a serializable transaction. Empty scopes and missing identifiers fail closed. The data source explicitly rejects null or undefined ORM predicates.

Agents inherit the base operations with an owner filter. Messages filter by both agent ID and the related agent's owner; their listing calls `super.list(scope)` for the newest 100 and reverses the result into chronological order. Message insertion locks the owned parent while persisting its child. `p-retry` retries only rolled-back serialization/deadlock conflicts, up to four retries; connection ambiguity and application errors are never replayed. Transaction callbacks contain database work only.

TypeORM `EntitySchema` definitions live beside their domains. Shared base columns keep IDs and ISO timestamp mapping consistent. Internal message relations and sequence values are excluded from public responses. Application services continue to depend on interfaces.

The other infrastructure replacements are `env-schema` for typed, validated environment settings and `async-lock` for per-agent asynchronous coordination. Agent lifecycle behavior remains a domain rule. Fastify/TypeBox already handle HTTP validation, Helmet and rate-limit handle transport protections, JOSE handles JWT cryptography, and Pi owns model streaming and session persistence.

Transport and use cases depend on interfaces. Pi and PostgreSQL can be replaced without changing the controllers or conversation coordinator.

## API

Requests and assertions are executable in [the Bruno collection](../../testing/api/bruno/bruno.json). Open `testing/api/bruno` in Bruno, select `Local`, and run the `requests` folder while `cluster:forward` is running. Requests are grouped by what they verify, and the folders run in order:

| Folder | Verifies |
| --- | --- |
| `01-health` | Liveness and database readiness, without authentication. |
| `02-authentication` | Missing, invalid, and wrong-audience tokens are rejected; obtains the test identities' tokens for the folders after it. |
| `03-agents` | Definition validation, creation, listing, reading, profile edits, avatar selection, and deletion. |
| `04-agent-capacity` | Several agents exist at once; the number is not limited by storage. |
| `05-conversation` | Message validation, an empty conversation, the unloaded runtime, and interrupting an idle agent. |
| `06-ownership` | Another identity cannot read, edit, message, or delete a teammate. |
| `07-artifacts` | Artifact listing and view links through the artifact service: authentication, unknown artifacts, and paths outside an artifact. |

After authentication, each folder creates the agents it needs and deletes them at its end, so a folder can be run on its own once `02-authentication` has run. `restart/before` and `restart/after` hold the restart phases that `pnpm test:restart` runs around replacing the pods. The `Local` environment holds the development test clients' secrets from `values.dev.yaml`. `pnpm test:api` invokes `bru run` directly with the same collection; there is no custom runner or HTTP client.

| Method | Path | Result |
| --- | --- | --- |
| GET | `/health/live` | Process liveness. |
| GET | `/health/ready` | Database readiness. |
| GET | `/v1/me` | Verified subject. |
| GET | `/v1/agents` | Caller-owned agent definitions. |
| POST | `/v1/agents` | Create `{ "name": "Chosen by the user", "systemPrompt": "...", "avatarId": "avatar-01", "inference": { "provider": "chatgpt", "model": "...", "effort": "medium" } }`. Avatar and inference selections are optional. |
| GET | `/v1/agents/:agentId` | Read a definition. |
| PATCH | `/v1/agents/:agentId` | Edit any supplied `name`, `systemPrompt`, `avatarId`, or complete `inference` selection; omitted fields keep their saved values. |
| GET | `/v1/providers/:provider/models` | Models and supported effort levels from the caller's active connection. |
| DELETE | `/v1/agents/:agentId` | Stop execution, delete the agent's files, and remove application records. |
| GET | `/v1/agents/:agentId/messages` | Latest 100 visible messages and `nextCursor`; `?before=<cursor>` reads earlier history. |
| POST | `/v1/agents/:agentId/messages` | Persist `{ "text": "..." }`, interrupt prior work, and return 202 with message/run IDs. |
| GET | `/v1/agents/:agentId/runtime` | `idle`, `running`, or `error`, plus the loaded session ID. |
| POST | `/v1/agents/:agentId/interrupt` | Abort generation and await in-flight tools. |
| GET | `/v1/artifacts` | Artifacts shared by the caller's teammates, with status, link, and authors. |
| POST | `/v1/artifact-views` | Exchange `{ "slug": "...", "path": "/optional" }` for a one-time `url` that opens the artifact on the artifact host. |

Request schemas reject unexpected properties, invalid IDs, empty messages, and excessive input. Bodies are bounded to 64 KiB. Routes reachable without authentication are rate limited per client address: sign-in at 20 requests a minute, session restore, logout, and the ChatGPT callback at 120. Authenticated routes are not rate limited, since the application has a single user. Security headers are applied, and authorization headers are redacted from logs. Public runtime errors do not contain provider responses or credentials.

Profile edits require at least one field and accept only the 64 built-in avatar IDs (`avatar-01` through `avatar-64`). The shared `@everything/agent-contracts` package defines the inputs and public response; its `/avatar` export defines stable IDs independently of artwork or animation states. Every definition response includes `avatarId`; creation without a selection defaults to `avatar-01`. The profile service depends on `AgentProfileStore`, and the PostgreSQL update includes the verified owner in its predicate. Missing and inaccessible IDs both return the same 404 response. Existing name-only PATCH requests remain valid.

## Persistence and execution

PostgreSQL has its own PVC and separate database roles/databases for Keycloak, Everything, and the artifact service, plus the `artifact_data` database holding each dynamic artifact's schema. Everything stores user-named agent definitions and visible conversation messages there. Pi's native JSONL history remains on disk. TypeORM owns database connections and runs tracked migrations through `everything_migrations`. Schema synchronization and automatic dropping are disabled. The initial migration creates the constrained schema; later schema changes add new migrations.

The avatar migration adds the constrained, non-null `agents.avatar_id` column and backfills existing definitions with `avatar-01`. The UI's Description field edits the existing `systemPrompt`; it does not introduce separate descriptive metadata. Saving a profile never starts or interrupts execution. On the next message, changes to the name, instructions, or inference selection reopen the same durable Pi session with the saved settings. Visible conversation history is preserved.

Teammates are created at runtime and are not limited in number, so their files share one volume (`everything-agents`, mounted at `/agents`), each teammate in a directory named by its ID. A volume per teammate, as the architecture page describes, would require redeploying the pod for every new teammate, because a running pod cannot gain volume mounts. The existing `everything-state` volume remains mounted, but inference no longer reads shared Pi credentials or provider defaults from it. The Everything container requests 3 GiB of memory with a 4 GiB limit, since every active teammate's session runs in it; PostgreSQL requests 512 MiB with a 1 GiB limit.

The `agent-inference` migration adds nullable `agents.inference` JSONB, containing the selected provider, model, and effort as one value. Existing teammates and creation requests without inference remain unassigned; sending to an unassigned teammate returns 503 `PROVIDER_UNAVAILABLE` and saves nothing. Both create and edit validate a supplied selection against the owner's active provider catalog and the effort levels supported by Pi. Profile-only edits can retain an unavailable selection so owners can still rename their teammates.

The create/edit form lists configured providers with a successful verification and no connection error. Creating a teammate through the modal requires a complete model selection. Model discovery uses the owner's credentials and makes no inference request; ChatGPT uses its account-visible catalog, Claude uses its paginated model list, and compatible endpoints use `/models`. Compatible servers without a model-list endpoint can use the model explicitly saved and verified in provider settings. Pi's catalog and supplemental local-model capabilities supply supported effort levels; unknown models use their default behavior without an explicit reasoning setting.

Each Pi session receives its selected model and effort in an isolated model runtime. Credentials remain encrypted in PostgreSQL and are resolved for that owner before every inference request, including serialized ChatGPT token refresh. A disconnected or failed connection cannot fall back to another owner's credentials or a machine-wide default. Session files contain the model choice and history, but no decrypted provider credentials.

### Model-provider connections

`GET /v1/providers` returns safe metadata for ChatGPT, Claude (`anthropic`), and an OpenAI-compatible endpoint. `PUT /v1/providers/:provider` saves API-key settings and checks them; `POST /v1/providers/:provider/verify` checks a saved connection; `DELETE /v1/providers/:provider` removes its credentials. ChatGPT uses `POST /v1/providers/chatgpt/authorize` and `/complete`. Every management operation requires the application's normal authentication and mutation-origin checks. No response contains API keys or tokens.

The tracked `provider_connections` migration stores one record per owner/provider. Credentials and pending OAuth attempts are encrypted using the existing chart-managed session encryption key, bound to the owner and provider. PostgreSQL persistence survives API pod replacement. Keep this key stable; rotating it requires reconnecting providers as well as signing in again. Provider credentials are entered through the application, never committed to chart values. Checks use real bounded inference requests; a model list or successful HTTP connection alone does not turn the icon green.

The `provider-checks` migration adds `last_checked_at` and backfills successful verification times. The API's singleton background worker checks due connections on startup and polls the persisted schedule once a minute, making an automatic inference check at most once every 24 hours per connection. It runs without an open browser. Each attempt is recorded before contacting the provider, including failed attempts, so reloads and restarts do not repeat checks. Due identities come from a bounded internal maintenance query; checks reload credentials under the owning connection's lock and skip records checked or disconnected since discovery. Manual checks and saved setting changes can trigger an earlier check. Successful connections stay Connected while a daily refresh is due or running; a failed result changes the status to Check failed. The UI displays the saved last-check time, and status polling itself never sends inference. Shutdown drains the current background request before closing PostgreSQL.

Set `global.externalHostname` for the installation's browser hostname. `global.publicOrigin` is a template that adds the scheme and port (development HTTP/8080, production HTTPS); Keycloak, API origin checks, production ingress, and chart notes resolve it consistently. ChatGPT's open-source registration currently requires an HTTP callback on `127.0.0.1`, even when the application uses another hostname. `services.everything.env.CHATGPT_REDIRECT_URI` defaults to `http://127.0.0.1:8080/v1/providers/chatgpt/callback`. The callback redirects to the configured public origin using a fragment, and the browser validates its initiating state before posting the code. It does not depend on cookies crossing between localhost and 127.0.0.1. For a remote installation where that loopback address cannot reach Everything, copy the full return URL from the sign-in tab into the dialog; no account tokens are copied. The official self-hosted flow also supports completing OAuth locally and securely transferring protected credentials; direct arbitrary-host OAuth callbacks are not supported by this open-source registration.

Local model addresses are resolved by the API pod, not the user's browser. Use an address reachable from that pod (for example a host/LAN address or `host.minikube.internal` for a model running on the Minikube host), with the server's API prefix. Requests refuse redirects so credentials cannot follow a redirect to another destination. Servers without model discovery can use an explicit model under Advanced settings.

Protocol references: [OpenAI registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [ChatGPT plan inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), and [Claude API](https://platform.claude.com/docs/en/api/overview). Live account access still requires the user's own sign-in or key; automated tests use controlled protocol responses and a local model fixture.

### Teammate runtime

Each teammate has exactly one ongoing user-facing conversation. Opening a teammate always returns to the same message history. This is a product rule across releases. Internal Pi sessions and background conversations never become separate user-visible conversations.

On the first turn, the model receives the teammate's name and saved Description (`systemPrompt`, in a `<description>` block it treats as its role), followed by the harness's sections on replying (confirm a task before starting it, send brief updates, and always finish with the outcome), the workspace and shared folder, artifacts, and Fleet. Pi adds a `<cwd>` section naming its working directory, the teammate's workspace `/workspace/<agent id>`, which the teammate's pod and Everything's container mount at the same path. If a turn ends without a reply, or keeps working after its last message, the teammate gets one private reminder to deliver the reply or the outcome. Tool descriptions and argument schemas accompany the request separately. The first user message is the only initial conversation history; existing teammates resume their native session, including prior turns and compaction summaries. Host `AGENTS.md`, `SYSTEM.md`, append files, skills, and extensions are not loaded, and Pi's default coding-assistant prompt is replaced. Name, Description, or model-setting edits take effect on the next user turn in the same session.

`GET /v1/agents/:agentId/messages` returns `{ messages, nextCursor }`, the latest 100 saved messages in insertion order. Pass `?before=<nextCursor>` for the preceding page. The cursor is a message ID checked against the same owner and teammate; inaccessible cursors return an empty page. Earlier history is retained without a conversation-length cap. Runtime status additionally reports `compacting` and `typing`, which is true from the first streamed part of a `send_message` call until it delivers the message. The UI shows typing bubbles only while `typing` is true and no other sign of work: no progress text, summarizing notice, or stop control. It polls every second while the teammate works, and never shows session IDs or model internals.

Automatic compaction uses Pi's native summarizer with the same owner-scoped provider, model, and effort as replies. It reserves up to 16,384 tokens (one quarter of smaller context windows) and retains up to 20,000 recent tokens (also bounded to one quarter). The context window and response cap come from the model list the provider serves when it reports them: llama.cpp-style `meta.n_ctx`, vLLM's `max_model_len`, LM Studio's `loaded_context_length`, Groq's `context_window` and `max_completion_tokens`, and OpenRouter-style `context_length` and `top_provider` fields. A single-model llama.cpp server that lists only its training context is asked for `/props` instead. Reported limits win over Pi's catalog, because a server may run a model with a different context than its maximum. A server that reports its context but no response cap gets a quarter of the context, at most 32,768 tokens. A model that neither its server nor the catalog describes keeps 32,768 tokens of context and 4,096 of response. Limits are read when a teammate's runtime loads: on its first turn after Everything starts, or after its profile changes. Resource loading completes before the harness applies these settings. Pi persists each summary checkpoint in the teammate's existing JSONL session, carries previous summaries into later compactions, and attempts compact-and-retry recovery on provider context overflow. PostgreSQL messages are never rewritten or removed by compaction. Summaries are lossy, so older context is represented by its important facts rather than verbatim recall; the full visible transcript remains available to the user.

The runtime waits for compaction and any recovery request before reporting completion. Summary failures report a safe error while preserving the transcript. `POST /v1/agents/:agentId/interrupt` cancels summarization as well as generation; the chat UI offers no stop control. Sending another message stops the active turn first. A model still needs enough context for its instructions and an individual message; automatic compaction removes the need to manually start another conversation, not the provider's per-request limits.

The teammate’s Pi session is reopened lazily on the next message after a restart. Runtime status is process-local and initially reports an unloaded `sessionId`; saved conversations and native context survive. User input aborts the current Pi turn, waits for it to settle, then starts the new turn. Different agents can run concurrently; same-agent operations are serialized. Everything runs as a single-replica StatefulSet, as does PostgreSQL: Kubernetes never starts a replacement pod until the previous one is confirmed gone, so two processes never run the same agents or open the same data directory, even when a node stops responding. The cost is that a pod on a failed node stays down until the node is removed or the pod is force-deleted. Keycloak keeps its state in PostgreSQL and runs as a Deployment.

Teammates have `send_message`, `file_read`, `file_write`, `bash`, and the [artifact tools](#apps). Pi's ordinary assistant output is private, even when it contains text. Deleting a teammate stops its model session, removes its durable definition and messages, then stops its tools pod before removing files. Reconciliation retries interrupted cleanup, including leftover workspace directories.

A successful user turn must deliver a visible reply. If the model finishes with only private text, the harness sends one internal reminder to call `send_message` in the same session. A second undelivered completion becomes a safe runtime error. Cancellation prevents this correction, and provider failures are not automatically retried by the delivery policy.

Already saved state must survive restart. An in-flight turn can be interrupted or lost, and is not replayed automatically. PVCs protect against pod replacement, not volume deletion or loss of the cluster.

### Generated API documentation

Teammates and their private subagents have the `everythion-api-docs` tool. It returns `{ agentId, definition }`, where `agentId` identifies the current saved teammate and `definition` is an OpenAPI 3.0.3 document. Call it with `{}` for the full API, or filter with `{ "path": "/v1/agents/:agentId/subagent", "method": "POST" }`. Paths accept both Fastify's `:agentId` and OpenAPI's `{agentId}` spelling, match at segment boundaries, and include descendants. Filtering retains referenced components. The harness instructs teammates to request this definition before writing apps or integrations against Everything.

`@fastify/swagger` reflects the routes registered inside the authenticated API scope and their TypeBox request and response schemas. Route registration is the source of truth: adding an endpoint or changing its schema updates the generated definition on the next startup without editing a separate endpoint catalog. Endpoint summaries and behavioral details live alongside the controller's schemas. The snapshot is published only after all routes are registered; reading it never runs a handler or accesses user data, credentials, or provider connections. Response schemas also describe the API's actual JSON serialization.

Authenticated consumers can fetch the same full definition at `GET /v1/openapi.json`; responses are marked `Cache-Control: no-store`. It documents bearer authentication through the app's `EVERYTHING_*` variables, inputs, success responses, the common safe error envelope, and the subagent wakeup lifecycle. Browser sign-in routes, OAuth callbacks, probes, and internal service endpoints are outside this authenticated API definition. Tests validate the generated document, its filtered form, and automatic reflection of new routes and changed constraints.

### Background subagent API

Authenticated consumers, including apps with the `everything-api` capability, can manage a teammate's private Pi subagents. Every request checks ownership of the saved teammate. These are the same sessions created by the `fork` tool: they share its model settings, tools, and workspace, and their replies can wake their parent. API-created subagents have `parentId: "main"`. They do not create another user-facing conversation or a Fleet workspace agent.

All paths below start with `/v1/agents/:agentId`:

| Method | Path | Request and response |
| --- | --- | --- |
| `POST` | `/subagent` | Body `{ "task": "Do background work", "context": false }`; returns `201` with `{ id, parentId, status }`. `task` is required; `context` defaults to `false`. Set it to `true` to copy the main session's current context. |
| `POST` | `/subagent/wakeup` | Body `{ "task": "Handle this remote event", "context": false }`; returns `202` with `{ id, parentId, status }`. Runs a temporary subagent and deletes it when it stops. |
| `GET` | `/subagent` | Returns `{ subagents: [{ id, parentId, status }] }`, including nested and tool-created sessions. |
| `DELETE` | `/subagent/:subagentId` | Stops and deletes the session, its descendants, and their saved transcripts; returns `204`. |
| `POST` | `/subagent/:subagentId/messages` | Body `{ "text": "Follow-up instructions" }`; returns `202` with `{ id, parentId, status }`. Wakes an idle or stopped session, or queues behind its active turn. |
| `GET` | `/subagent/:subagentId/messages` | Returns `{ messages, nextCursor }`, with the latest 100 text messages in chronological order. Use `?before=<nextCursor>` for earlier messages. |

Tasks and messages must contain non-whitespace text and are limited to 32,000 characters. Status is `running`, `queued`, `idle`, `stopped`, or `error`. Creation returns once the session is opened and its task is queued, without waiting for its result. At most eight subagents run concurrently per teammate; creation at capacity returns `409`, while messages to existing sessions wait for a slot. API input does not interrupt the main conversation or appear as a user message in it. Background results reach the parent through the existing private messaging path, so the main teammate can subsequently send a visible reply.

History contains the subagent's incoming text, assistant text, and successfully delivered explicit messages. It excludes inherited parent context, thinking, arbitrary tool calls and results, and provider errors. Message IDs are opaque cursors scoped to that subagent; an inaccessible cursor returns an empty page. Missing or inaccessible teammates and subagents return `404`. Creation and messaging require an available model runtime; listing, reading history, and deleting saved sessions work without a connected provider.

Native transcripts survive restart, and restored sessions report `stopped` until explicitly messaged. A queued message enters the transcript when its turn starts; queues and in-flight work are process-local and can be lost on stop, deletion, or restart. They are not replayed automatically.

Use `POST /v1/agents/:agentId/subagent/wakeup` for remote events. Each accepted request creates a new temporary subagent and returns without waiting for the result. The prompt runs through the normal model/tool loop; its messages and final result can wake the main teammate through the existing private routing. Once the subagent has no more turns to run, its session, descendants, and transcripts are deleted. Cleanup also runs after failure, explicit cancellation, or graceful shutdown. If the process crashes, temporary histories and their descendants are removed when that teammate's sessions are next opened or inspected, without replaying the event. Files the subagent wrote in the workspace and messages already delivered to main remain. Ordinary subagents retain their histories as before.

Wakeup uses the same ownership checks, task limit, optional context copying, and eight-subagent concurrency limit as creation. At capacity it returns `409` without accepting the event. Every successful request is a separate event; callers are responsible for avoiding duplicate submissions. The returned ID is useful only while the temporary session exists; subsequent history or messaging requests return `404` after cleanup.

## Teammate tools pods

Everything reconciles persisted teammate records on startup and every five seconds. Every teammate, including one without a connected model, gets a one-replica StatefulSet and a private ClusterIP Service. Kubernetes recreates missing pods immediately; Everything recreates missing workloads and Services, updates them when the template changes, and removes orphans. Controller restarts leave tools pods running. There is no idle shutdown.

The chart's `services.teammate` entry has zero replicas and supplies the reusable pod template, image, probes, and CPU/memory limits. Everything copies that template for each teammate. The deployment scripts discover its image through the rendered chart and reload it alongside the other images. Everything mounts the `everything-agents` volume at `/workspace`, with each teammate's files in `/workspace/<agent id>` and a `shared` folder beside them, which Everything creates at startup. Each tools pod mounts only its teammate's folder, at that same `/workspace/<agent id>`, and the shared folder at `/workspace/shared`; it never sees other teammates' folders, and an empty read-only mount hides `.pi`. Because a path names the same files in a teammate's pod, in Everything, and so in fleetd, a teammate can hand Fleet a template folder, and the path Fleet records stays valid. The prompt asks teammates to keep folders they hand to Fleet, such as templates (`file:///workspace/shared/app`), in the shared folder, so every teammate can see and update them, and to use their own folder only for folders no other teammate needs. The file tools and Bash accept paths in the teammate's own folder and the shared folder; relative paths are in its own folder. Pods are scheduled alongside Everything because that existing PVC is ReadWriteOnce. Workspace and shared files survive replacement; `/tmp` does not. The volume has no per-teammate disk quota.

The tools image is a general development environment on Debian trixie: Node.js 24.21.0 with npm, Python 3.14.8 with pip and venv, Ruby 4.0.7 with Bundler, Go 1.27.2, gcc/g++ and make, git, curl, jq, zip, xz, and Debian's Chromium. Python, Ruby, and Go are copied from their official trixie images, so they link against the same system libraries, and the image build fails if a copied program is missing one. Commands run as UID 1000 without root, so they cannot use `apt-get`. HOME is the teammate's workspace, `/workspace/<agent id>`, which the workspace API sets for every command along with the npm, gem, and Go install locations. `pip install --user`, `npm install -g`, `gem install`, Bundler, and `go install` write to `~/.local`, which is on PATH, so installed tools persist with the workspace files. The account's home is the workspace too: the image's `/etc/passwd` names a fixed home and its file system is read-only, so each tools pod gets an `account` init container that copies the account database with UID 1000's home set to `/workspace/<agent id>`, mounted over `/etc/passwd`. Programs that read the account database instead of HOME, such as OpenSSH, find the teammate's `~/.ssh`. Download and build caches for npm, pip, Bundler, Go, and Chromium go to `/tmp/cache`, so this data stays off the shared volume, and a replaced pod rebuilds it. `/tmp` holds up to 4 GiB, and exceeding that evicts the pod. Chromium runs without its sandbox, which needs user namespaces or a setuid helper that the tools container's security context rules out, and it always runs headless. `CHROME_PATH` and `PUPPETEER_EXECUTABLE_PATH` point browser libraries at Chromium, and Puppeteer and Playwright skip their own browser downloads. A 512 MiB memory-backed `/dev/shm` serves browsers and multiprocessing. Each tools pod requests 25m CPU and 64 MiB of memory, and can use up to 2 CPUs and 2 GiB.

Everything invokes an internal authenticated HTTP API; each pod receives a distinct derived token, never the controller key, provider credentials, database credentials, or a Kubernetes service-account token. File writes replace UTF-8 content (up to 1 MiB), and reads return bounded byte slices (up to 128 KiB) with continuation offsets. Bash receives only an allowlist of the image's locale, toolchain, and cache variables, never the pod's token or the API's own settings. It runs inside the tools container, defaults to 30 seconds (maximum 120), and returns capped combined output (64 KiB), exit status, timeout, and truncation flags. Commands run concurrently without an application concurrency limit. Each has its own Linux subreaper, which kills and reaps only that command's descendants on completion, timeout, or interruption, including detached children. Disconnecting one caller leaves other commands running; API shutdown interrupts them all. Publish or deploy apps for persistent hosting. Oversized responses are bounded again in Everything.

The isolation boundary is the tools container and its workspace mount, with a non-root user, read-only image, dropped capabilities, and CPU/memory limits. No network policies or process-count limits are installed. Tools share the cluster network. This design isolates command execution from the main Everything process; it is not intended as a hostile multi-tenant security boundary.

## Apps

The Apps page supports search and status-first, newest-update ordering. Owner-scoped browser actions at `POST /v1/artifacts/:appId/start`, `POST /v1/artifacts/:appId/stop`, and `DELETE /v1/artifacts/:appId` resume, pause, or remove apps. Start reuses the saved release and runtime settings. Static pages can pause too; migration `1792195200000` preserves existing published pages as running. Browser deletion checks that the app is still stopped under the same lock used for releases, before removing data. Manual changes record the authenticated owner as “You”.

The interface and teammate tools call this feature apps. The internal service, API routes, database, and deployment settings retain their `artifact` identifiers.

Apps are shared, linkable pages and applications that teammates publish; every teammate can change any of them. The app service tracks them in its own `artifact` database, stores uploaded files by SHA-256 on its `artifact-content` volume, builds images, runs dynamic apps, and serves all of them on the app host. [The architecture page](../../planning/documents/architecture.md#apps) describes the design.

| Component | Where it runs |
| --- | --- |
| App service | StatefulSet `artifact`. Port `http` (8080) serves the app host through the `everything-artifacts` Ingress; port `internal` (8081) serves the internal API inside the cluster. |
| Registry | StatefulSet `registry`, CNCF Distribution with a password file. Nodes pull through its own Ingress, at `global.externalRegistryHostname` over HTTPS; build jobs push to its Service inside the cluster. |
| Builds | One rootless BuildKit Job per build in `everything-builds`, limited to 30 minutes. It downloads its source from the internal API with a per-build token and pushes to the registry inside the cluster. |
| Dynamic apps | A Deployment, or a one-replica StatefulSet when it has a disk, plus a Service, in `everything-artifacts`. Pods run unprivileged with a writable `/tmp`, 512 MiB of memory, and one CPU. |

Locally, `cluster:forward` serves the app host at `http://localhost:8081` beside the application at `http://localhost:8080`. A different port is a different origin on the same site: app pages cannot call the API as the user, and the app host's cookie still works in the app. Traefik serves the two Ingresses on separate entrypoints, `web` and `artifacts`, named in `values.dev.yaml`; rerun `.devcontainer/install-traefik.sh` in an existing devcontainer to add the `artifacts` entrypoint. Other clusters set `global.externalArtifactHostname` to a sibling of `global.externalHostname`, such as `artifacts.example.com`.

Locally the registry's hostname is `registry.everything.test`, served on Traefik's `websecure` entrypoint with Traefik's self-signed certificate. Neither pods nor the node resolve it through public DNS: `.devcontainer/install-traefik.sh` adds a CoreDNS rule that resolves names under `.test` to Traefik for pods, and `deployment/script/configure-local-registry.sh`, which `cluster:up` and the devcontainer's startup run, maps the hostname to Traefik in the node's hosts file and has the node's container runtime accept the certificate for that host only. `values.dev.yaml` has Fleet and the Docker engine in Everything's pod accept it too. Rerun `.devcontainer/install-traefik.sh` in an existing devcontainer to add the CoreDNS rule.

Each teammate's Pi session has `create_app`, `list_apps`, `get_app`, `update_app`, `delete_app`, `checkout_app`, `publish_app`, `build_app`, `get_app_build`, `deploy_app`, `stop_app`, `get_app_logs`, and `view_app`. Directories resolve relative to the teammate's workspace, or absolute in it or in `/workspace/shared`; anything else is refused. The workspace itself is refused: it is also the teammate's home, holding installed tools and settings. Its `.pi` directory is refused as a directory or checkout destination, even through symbolic links, and is never uploaded; `.git` directories and symbolic links are never uploaded either, and builds follow `.dockerignore`. Only content the app service lacks is uploaded. Everything calls the internal API with the `everything-artifact-client` service account and names the acting teammate in `X-Everything-Actor-Id` and `X-Everything-Actor-Name`. A change based on an older release than the live one fails with `RELEASE_CONFLICT` naming the newer release's author. The file and Bash tools edit these same durable workspace files before publishing or building.

Every app is private. The UI asks `POST /v1/artifact-views` for a one-time link, valid for two minutes, which the app host exchanges for its own 12-hour HttpOnly cookie before opening the app. A signed-out visit goes to `/apps/open` in the app, which repeats the exchange after sign-in. Requests to a dynamic app are forwarded to its Service without the app host's or the application's login cookies, with the slug prefix removed, `X-Forwarded-Prefix` set, and root-relative redirects kept under the prefix. WebSockets are not forwarded yet.

Teammates check their work with `view_app`, which opens an app from the teammate's pod the way the user sees it. Everything asks the internal API (`POST /internal/v1/owners/:ownerId/artifacts/:artifact/view-passes`) for a pass with its existing service account, so pods never hold Keycloak credentials. A pass is a random `everything_view_` token, stored only as a SHA-256 hash in `view_passes`, that opens only that app of that owner for ten minutes; the hourly credential cleanup deletes expired passes, and deleting the app deletes its passes. The tool returns URLs on the in-cluster app host (`ARTIFACT_HOST_URL`, `http://artifact.<release namespace>.svc.cluster.local:8080`) and ready-to-run commands: curl sends the pass as `Authorization: Bearer`, and a single headless Chromium run opens `/_teammate-access?token=…`, which stores the pass in an HttpOnly `everything-teammate-pass` cookie limited to the app's path, then redirects to the page; the link works again until the pass expires. The cookie is `Secure` only when the request arrived over HTTPS, because browsers drop `Secure` cookies over plain HTTP. The host accepts `Authorization` only when it carries the pass prefix, so an app's own bearer tokens pass through unchanged; the pass header and cookie never reach a dynamic app. A pass for another app, an unknown app, and another owner's app all answer 404; an expired or unknown pass answers 401. These links work only inside the cluster, so teammates share the app's own link with the user.

A dynamic app's pod receives `PORT`, `BASE_PATH` (its `/slug` prefix; requests arrive with the prefix removed, so apps serve routes from `/` and use `BASE_PATH` only for absolute links and asset URLs), and, when deployed with `database: true`, `DATABASE_URL` and the `PG*` variables for its own role and schema in `artifact_data`. A disk (`diskGi`) is a volume mounted at `/data`; its size is fixed once created. Stopping deletes the workload and keeps its Secret, disk, and schema. Deleting the app removes them all and drops its role. The service stores the desired state in PostgreSQL and reconciles Kubernetes at startup, after each change, and every five minutes; images are referenced by digest. It creates each app's database Secret at runtime, since those credentials do not exist at install time.

Dynamic apps can request Everything API access through `deploy_app({ app: "my-app", capabilities: ["everything-api"] })`. The first deployment has no capabilities. Omitted capabilities retain the live deployment's settings; an explicit `capabilities: []` removes them. Existing deployments are migrated to an empty list. Static apps cannot request backend capabilities.

The artifact service provisions a dedicated confidential Keycloak client for each app and injects these reserved environment variables through an app-owned Kubernetes Secret:

| Variable                   | Value                                                                                                     |
| -------------------------- | --------------------------------------------------------------------------------------------------------- |
| `EVERYTHING_API_URL`       | Internal API origin, for example `http://everything.everything.svc.cluster.local:8080`; append `/v1/...`. |
| `EVERYTHING_CLIENT_ID`     | Stable client ID derived from the app UUID.                                                               |
| `EVERYTHING_CLIENT_SECRET` | That app's generated client secret.                                                                       |
| `EVERYTHING_TOKEN_URL`     | Internal Keycloak token endpoint ending in `/auth/realms/everything/protocol/openid-connect/token`.       |

The backend posts form-encoded `grant_type=client_credentials`, `client_id`, and `client_secret` to `EVERYTHING_TOKEN_URL`, then sends `Authorization: Bearer <access_token>` to the Everything API. Keycloak signs the app ID and owner claims, and the API resolves only properly provisioned app-client tokens to that owner after validating the signature, issuer, audience, and expiry. This grants the owner's existing API access, including teammates and conversations; there are no narrower per-operation permissions. Credentials and tokens stay on the backend. They are not returned by app tools, stored in deployment history, or forwarded to browser code. These clients have no management roles or artifact-service audience and cannot use password or browser login flows.

Redeploying or stopping an app preserves its client and secret. Disabling the capability or deleting the app removes its Keycloak client and Kubernetes Secret. Already issued access tokens remain usable for up to five minutes, plus the verifier's five-second clock tolerance. If a secret changes, reconciliation rolls the app's pod. Background reconciliation uses the same per-app lock as deployment and deletion, so a stale observation cannot recreate a deleted client's credentials.

The public artifact proxy checks dynamic app responses against that app's provisioned `EVERYTHING_CLIENT_SECRET`. It loads credentials before forwarding and again before releasing the response, checks every response header, and scans body bytes across chunk boundaries. It also recognizes common JSON, URL, base64, and UTF-16 representations. Gzip, deflate, and Brotli bodies are decompressed for inspection and forwarded decoded. A match or an inspection failure returns a generic 502 without upstream headers; if safe bytes have already been streamed, the connection closes before the matching bytes are sent. Credentials and response data are never included in protection errors or logs. Protected responses use `Cache-Control: no-store`; the proxy removes range and cache-validation request headers and refuses partial responses, 304 responses, and unsupported compression. Apps without provisioned credentials keep their usual proxy behavior.

This is a safety net for accidental credential exposure through the public app host. It does not inspect direct cluster traffic, app egress, access tokens, arbitrarily transformed secrets, or secrets split across separate responses. Backend code must still keep credentials private. WebSockets remain unsupported.

Provisioning uses the separate `everything-app-provisioner` service account with Keycloak's `realm-management/manage-clients` role. Only the artifact service receives its secret, supplied by `secrets.app-provisioner-auth.client-secret`; development supplies a fixed test value in `values.dev.yaml`. The production realm includes this service identity but no test clients or human users. Private cluster callers can use HTTP token requests with `sslRequired: external`, while ingress supplies TLS for public requests and `KC_HOSTNAME` fixes the public issuer. See Keycloak's [SSL modes](https://www.keycloak.org/docs/latest/server_admin/index.html#_ssl_modes) and [Admin REST API](https://www.keycloak.org/docs-api/latest/rest-api/index.html).

Keycloak does not update existing realms from startup imports. `pnpm cluster:up` runs `deployment/script/provision-app-client.sh` after rollout to create or update only the provisioning service client, its management role, and the realm's internal HTTP policy; users and existing clients are preserved. For an existing remote installation, supply the new secret, deploy the chart and Keycloak image, then run `/opt/keycloak/bin/provision-app-client.sh` in the Keycloak container using a configured administrator. This upgrade uses a temporary admin credential cache and removes it when finished. Fresh installations import the service identity directly.

Each app keeps its 20 newest revisions, builds, and deployments, always including the live ones. Uploaded content and registry images are not yet garbage-collected.

PostgreSQL creates the `artifact` role and the `artifact` and `artifact_data` databases only when it initializes an empty data directory, and Keycloak imports the `everything-artifact-client` client only into a new realm. An installation created before the app service needs both added once, following `services/postgres/config/initialize.sh` and `everything-realm.json`; locally, `pnpm cluster:down` and `pnpm cluster:up` start over.

## Fleet

[Fleet](https://github.com/BenjaminBenetti/fleet-man) is the orchestrator teammates delegate work to. Its daemon, fleetd, runs inside Everything's container, is connected to the cluster, and gives every teammate its MCP tools.

| Component | Where it runs |
| --- | --- |
| fleetd | A child process of Everything in the `api` container, restarted with backoff when it exits on its own and stopped with Everything. Its home is the 32 GiB `everything-fleet` volume at `/fleet`: Fleet's own state in `/fleet/.fleet`, its kubeconfig and Docker login, and the repositories it checks out. |
| Docker | The `docker` native sidecar of Everything's pod: a privileged Docker engine listening only on `/run/docker-socket/docker.sock`, which fleetd and the devcontainer CLI build devcontainer images with. Its images and build cache are scratch space, rebuilt with the pod. |
| Instances | The StatefulSets, Jobs, caches, and disks Fleet creates in `everything-fleet` (`global.fleetNamespace`). |

`fleet.version` in `values.yaml` pins the release. At startup Everything downloads fleetd for its own architecture, and the pod build and tmux bundle Fleet copies into instances for both amd64 and arm64, into `/fleet/.fleet/bin`. Each file must match its SHA-256 in `fleet.checksums`: a file is downloaded only when it is missing or differs, and one that does not match its pin is never installed. fleetd finds the pod files there, so it downloads nothing itself. To change the version, update it and all six checksums together, from the release's `checksums.txt` or `sha256sum` of its files.

Everything then writes `/fleet/.kube/config`, a kubeconfig for the cluster it runs in that names its service account's token file, so token rotation needs no restart. It adds the Fleet connection `everything` in `everything-fleet` on first start, and on every start sets the connection fields it manages: image delivery through the registry at `artifactRegistry.pullHost`, whose certificate Fleet verifies unless `FLEET_REGISTRY_INSECURE` is set, as `values.dev.yaml` does for Traefik's self-signed one; and `global.storageClassName` for instance disks, where empty lets Fleet choose. Fleet keeps every other setting as it or a user left it.

Whether instances may run privileged pods, which Docker inside an instance needs, is the user's choice: **Settings → Workers → Privileged workers** in the app, backed by `GET` and `PUT /v1/settings/workers`. Everything keeps it on the connection itself (`allow_privileged`), so Fleet's own client shows the same value. A new connection starts with it off, and so does one where it is unset, since Fleet would otherwise decide by the kind of cluster: allowed on local clusters such as Minikube, forbidden elsewhere. Everything changes it only when the user does. The setting can be read and changed once Fleet is running; until then the API answers 503 `WORKERS_UNAVAILABLE` and the dialog offers a retry.

Fleet pushes each image to the registry's hostname and names it by that address, which nodes pull from. The Docker engine in Everything's pod reaches the hostname through the ingress, as the nodes do, and Fleet builds the pull Secret nodes use from the registry login Everything writes to `/fleet/.docker/config.json`.

fleetd receives only `PATH`, `LANG`, `TZ`, and `DOCKER_HOST` from Everything's environment, with `/fleet` as `HOME`; devcontainers that read `${localEnv:…}` see none of Everything's settings or secrets. The `fleet` command in the container runs Fleet's client with the same home, so it reaches Everything's fleetd:

```sh
kubectl --context minikube -n everything exec -it everything-0 -c api -- fleet cluster ls everything
kubectl --context minikube -n everything exec -it everything-0 -c api -- fleet cluster test everything
```

A `fleet` command that finds no daemon starts one itself, with the calling shell's environment; Everything's supervisor retries until that daemon exits.

fleetd serves its MCP tools over Streamable HTTP on loopback, publishing the port in `/fleet/.fleet/mcp.port` and the bearer token it requires in `/fleet/.fleet/mcp.token`. Once Fleet is up, Everything finds the server there, and every teammate's Pi session connects to it through Pi's MCP support, with Fleet's tools named `mcp__fleet__<tool>`; a session opened while Fleet starts gets them once it runs. The tools are deferred: requests carry only Pi's `tool_search` tool and a line naming Fleet's server in the prompt, and a search declares the matching Fleet tools for the rest of the conversation. Declaring all 31 up front would add about 21,000 characters to every model request. Sessions read no `mcp.json` and connect no other server. The token stays in Everything's process: it is in neither the model's context nor the session files. The teammate prompt's Workers section explains how Everything uses Fleet: instances are workers that teammates dispatch for tasks likely to take more than about 10 minutes, or for background and recurring jobs, starting from a Git repository or a template folder and usually working through a coding agent set up in the worker, with shorter tasks left to the teammate's background forks; sign-in links and codes from tools in a worker, such as Claude Code, go to the user, and the user's reply is entered in the worker's session. Fleet's tools describe themselves, so the Fleet section states only how Fleet fits into Everything: create instances on the `everything` connection, and Fleet sees the teammate's workspace and the shared folder at the same paths, with folders handed to Fleet, such as templates, kept in the shared folder. With privileged workers on, a teammate with Fleet's tools can run privileged pods and so do anything in the cluster; this follows the single-user security posture.

fleetd clones repositories with Git. Public repositories clone over HTTPS without credentials. SSH remotes use `/fleet/.ssh`, because the container's account has Fleet's home as its home directory, which OpenSSH reads instead of `$HOME`: host keys a user accepts in Fleet's prompt are saved to `/fleet/.ssh/known_hosts`, and fleetd authenticates with the SSH agent of a connected Fleet client or, failing that, a key in `/fleet/.ssh`, such as a deploy key. A client started through `kubectl exec` has no agent to offer.

## Browser sessions

The welcome page submits a username and password to `POST /v1/session` on the same origin. Everything exchanges them with Keycloak over its internal HTTP endpoint using the dedicated confidential `everything-web` client. The API forwards the configured public scheme and host to Keycloak, matching the chart's `xforwarded` proxy settings and production HTTPS policy. The UI never navigates to Keycloak or receives its access/refresh tokens. `GET /v1/session` returns only the display profile; `POST /v1/session/logout` deletes the session and clears its cookie. Existing bearer API clients continue to work.

The cookie is host-only, HttpOnly, SameSite=Strict, and Secure with a `__Host-` prefix on HTTPS. Local HTTP uses an unprefixed development cookie. Login, logout, and cookie-authenticated mutations require the exact configured `PUBLIC_ORIGIN`; requests with explicit bearer authorization remain independent of cookie policy. Login attempts are limited to 20 per minute per client IP, with Keycloak's account-level brute-force protection also enabled. Credentials and cookies are redacted from request logs, and session responses use `Cache-Control: no-store`.

The `browser_sessions` table stores a hash of the random 256-bit cookie capability and JOSE A256GCM-encrypted Keycloak grants. Passwords are never persisted. Sessions expire after at most eight hours, or sooner at Keycloak's refresh expiry. Refreshes serialize per session in the existing single API replica; no browser tab can race another refresh. Each refresh still verifies issuer, signature, audience, and subject. Logout invalidates the stored capability before best-effort Keycloak revocation, so local logout still works during a provider outage. Expired records are removed when presented and the authenticated owner's expired records are pruned on successful sign-in. A database copy alone cannot decrypt the grants; keep the encryption key separate from database backups. Rotating that key signs out existing browser sessions.

The Helm chart requires `secrets.browser-auth.client-secret` and `secrets.browser-auth.session-encryption-key`. Supply a high-entropy client secret and a base64-encoded 32-byte encryption key in the external credentials values file. Generate each with `openssl rand -base64 32`. Only `values.dev.yaml` contains fixed public development values. The API receives both secrets; Keycloak receives the client secret for realm import; the frontend receives neither. The tracked migration runs at API startup. A stable encryption key and PostgreSQL volume preserve sessions through pod replacements.

Keycloak's startup import does not update an existing realm. For an existing installation, create or update `everything-web` through Keycloak's admin API using the client definition in `deployment/helm/files/keycloak/everything-realm.json`, with `secret` set to the same externally supplied chart value. Use client-secret authentication, Direct Access Grants enabled, standard/implicit/service-account flows disabled, no redirects or web origins, and the existing `everything-api` audience mapper. Disable the superseded `everything-ui` public client after the new UI is deployed. Do not delete the realm or its users. New installations import the correct client automatically.

This is a password-only login flow as requested. Keycloak calls it **Direct Access Grants**. It does not support browser authentication steps such as passkeys, federated redirects, required actions, or interactive MFA; accounts requiring these steps cannot complete this form. OAuth's current security guidance discourages this grant; adding those capabilities requires revisiting the authentication flow. See [Keycloak's grant documentation](https://www.keycloak.org/securing-apps/oidc-layers) and [OAuth Security Best Current Practice, section 2.4](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.4).
