# Telemetry

The Telemetry page (desktop only, after Keys in the sidebar) shows why something didn’t work: a model or provider error that a teammate turned into “Your teammate couldn’t finish replying”, a failed request to Everything, or the requests, database queries, and tool calls around it. Everything records them with OpenTelemetry, stores them in a single [OpenObserve](https://github.com/openobserve/openobserve) node for about a week, and reads them back through its own API, so the page needs no OpenObserve login and each owner sees only their own records.

```text
Everything (API + Pi runtime) ── OTLP/HTTP, Basic auth ──▶ openobserve (StatefulSet, PVC, ClusterIP only)
        ▲                                                         │
        └──────── /v1/telemetry/* (owner-scoped SQL it builds) ◀──┘
Browser ── same-origin session ──▶ /v1/telemetry/*
```

## What is recorded

Only the Everything API process exports telemetry. Its instrumentation is preloaded with `node --import ./build/telemetry/bootstrap/instrumentation.js` (the container's command and `pnpm start`), before Fastify, `pg`, or anything it instruments loads.

| Source | Recorded as | Notes |
| --- | --- | --- |
| Model requests | `provider.request` spans for each HTTP attempt, timed until the provider’s response headers, with status, the provider’s request ID, `Retry-After`, and for error responses the provider’s error code and, [unless error text is withheld](#privacy-and-redaction), an excerpt of its error message. | Attempts are numbered when an SDK retries; Everything’s own turns make one attempt, since Pi’s retries are off. A failure is diagnosed from its final attempt only: a network failure after a retried 429 is a network failure, while each attempt’s span keeps its own response. The streamed response belongs to the prompt’s span, which records a stream that fails after a successful response. |
| Model failures | `model.request.failed` events with a category (`rate_limit`, `quota`, `overloaded`, `context_length`, `authentication`, `stream_interrupted`, …), code, HTTP status, request ID, attempts, whether retrying may help, provider, model, and, unless error text is withheld, an excerpt of the error’s message. | Captured from Pi’s final assistant message before the runtime reduces it to a generic error, including streams that fail after HTTP 200. A stop is recorded separately as `model.request.cancelled`. |
| Teammate turns | A `teammate.turn` span per turn, starting its own trace linked to the request that started it, with a [preview](#content-previews) of the message the turn answered; `teammate.prompt` spans, each saying whether its text was that message, Everything’s reminder to reply, or a private message, never the text itself; `teammate.tool` spans (name, duration, failed or not, and a preview of the call’s arguments); and `teammate.compaction` spans. `turn.failed` and `turn.cancelled` events record the outcome. | Background forks and monitor wakeups record their prompts as traces of their own, and so does a message a fork sends to the main conversation, even when it waits behind a user’s turn; it is linked to the work that sent it, never part of that turn’s run. Tool results are not recorded, and a tool’s name only when it is a well-formed identifier. |
| Context compaction | `compaction.failed` and `compaction.cancelled` events, with the reason, whether Pi will retry, and the failure’s category, code, and status. | |
| Requests to Everything | Server spans named by route (`POST /v1/agents/:agentId/messages`), with status, and an `http.request.failed` event for 5xx responses: the error’s class, code, and stack frames as code locations for unexpected failures, and, if error text is recorded, its redacted message and those of its causes. | `/health` probes aren’t traced. Successful, quick `GET`/`HEAD` requests are kept at `TELEMETRY_READ_SAMPLE_RATIO` (5%); failed, client-error, and slow (≥2 s) reads are kept with every child span. |
| Dependencies | `fetch` (Undici) client spans and PostgreSQL query spans inside traced work, with each query’s statement as its [shape](#content-previews). | Parameter values and connection strings are never recorded; literals written into a statement become `?`. |
| Background warnings | `app.warning` events for Fleet, SSH key synchronization, workspace reconciliation, monitor delivery, update summaries, provider checks, and voice. | They belong to no owner, so they appear on nobody’s Telemetry page; see [Operator access](#operator-access). The same lines still go to standard error. |

Not collected: logs of other pods (UI, artifact, Keycloak, PostgreSQL, registry, voice, upgrader, teammate pods, Fleet instances), standard output or Fastify’s access log, Kubernetes events, metrics, browser errors, and anything in Pi’s private session files. There is no cluster-wide log collector.

## Privacy and redaction

Records are made safe in the process, before anything holds them for export, and again as they are exported:

- Each span is made safe as it ends, and each event as it is recorded, before the read-request filter or an export queue holds it. The queues hold a redacted copy of their own, with only what export would send: never the SDK’s record, so a credential, error text, or content left out isn’t kept waiting there. A record that can’t be made safe is dropped and counted with the queues’ other dropped records. This covers telemetry’s own buffers, not the rest of the process’s memory: while a span is being recorded, the SDK’s live span still holds what instrumentation set on it.

- Only allowlisted attributes leave the process: Everything’s own, plus HTTP method, route, status, host, path, database system and operation, a statement’s shape, and error type. Anything else a library records, such as headers, user agents, client addresses, SQL parameter values, or connection strings, is dropped. URLs lose user information, query strings, and fragments, and credentials in their paths, such as a key in a gateway’s base path, are redacted, including percent-encoded ones and ones after an encoded `?` or `#`. Identifiers, such as a tool name a model chose, an error type, or a host, are kept only when well-formed, and are redacted like any other text, since a well-formed identifier can still be a key. One that holds the redaction marker is kept only when each marker is a complete part of it, such as `tool-[redacted]`; a marker joined to other text, such as `password:[redacted]…` with more after it, is dropped. Span links keep only the IDs of the spans that started the work: at most eight, each a lowercase, non-zero W3C trace and span ID with its flags as one byte, and none of a link’s attributes or trace state.
- **Error text is recorded by default**, because explaining a failure is what the page is for. With `telemetry.includeErrorText: true`, the default, error text is redacted and cut to 400 characters (a provider’s excerpt to 300). Only an error’s own message is kept: the `message` of a provider’s JSON error body, or an SDK or transport message such as `Connection error.`. A body’s other fields, a body without a message, other serialized JSON such as an array or a JSON string (as an SDK reports a stream error whose `error` isn’t an object), and markup or other response bodies are never kept, nor used to choose a category. The text can quote part of a prompt or other private text, which redaction does not remove; it is visible only to the record’s owner, for the retention period.
- **Withholding error text.** With `telemetry.includeErrorText: false`, Everything leaves that text out of every record before export: event messages, the status messages of its own and of instrumented libraries’ spans, exception messages, and the messages of nested causes. Records keep structured facts: category, provider code or error type, HTTP status, provider request ID, provider and model, attempts, whether retrying may help, Everything’s own status text, its plain-language diagnosis and next step, and stack frames as code locations. Everything’s own status text comes from a fixed list: `Model request failed:` with one of the failure categories, `Context compaction failed`, and `HTTP` with a status. Any other status, including text that only begins the same way, is withheld. A record whose text was left out is marked, and the page says the text was withheld rather than showing nothing.
- **Content previews are recorded by default** too; see [Content previews](#content-previews). `telemetry.includeContent: false` leaves them out before export; unset, it follows `telemetry.includeErrorText`, so an installation that withholds error text withholds content too. A span whose previews were left out is marked, and the page says so.
- Changing either setting affects records made after Everything restarts with it, not records already stored: text that was withheld can’t be recovered, and nothing is backfilled.
- In every mode, every text value is redacted for credential shapes (bearer and basic tokens, JWTs, provider API keys, cloud keys, private keys, `name=value` secrets in text, JSON, or headers, URL credentials and query strings, long opaque tokens, and email addresses) and bounded, with `…[truncated]` marking a cut. Text with percent-encoded ASCII characters is checked again decoded, at most three times over within the same bounded window, so `api%5Fkey%3D…` or a key in an encoded URL path, even one encoded twice, is redacted too. No other encoding is decoded: a credential written in base64, as HTML entities, or percent-encoded more than three times isn’t recognized. Error descriptions read only an error’s class, code, status, message, causes (three deep), and stack frames, never response bodies or other properties an SDK attaches. A value that is exactly `[redacted]`, as redaction leaves one, is kept as it is, so redacting twice changes nothing, but a value that only begins with it, such as `password="[redacted]…"` with more after the marker, is redacted whole, in assignments, cookie headers, authorization credentials, and the names SQL quoted identifiers spell. Redaction recognizes these shapes; it isn’t data loss prevention, can’t promise to find every secret written some other way, and doesn’t remove ordinary private text.
- Only the first `2 × limit + 512` characters of any text are examined, so redaction takes the same short time however long or unusual the text is, and a credential the cut splits leaves no fragment.

## Content previews

Each preview is made where the content is, redacted for credentials and bounded, made safe again with its span before any buffer holds it, and checked again at export. Each holds at most 2,000 bytes of UTF-8, cut on whole characters, and says when it was cut; a preview is never the whole content once it says so.

| Preview | Where | What it holds |
| --- | --- | --- |
| Message sent to your teammate | The `teammate.turn` span | The message the turn answered, as it was sent to the conversation: whole when it fits, otherwise its start and its last 500 bytes, where a question after a long paste usually is, with the length of the whole message. It is taken where the conversation starts the turn, so Everything’s reminders, private messages between sessions, background tasks, the teammate’s instructions, summaries of earlier context, and the model’s thinking or responses are never part of it. The rest of the conversation stays in the conversation. |
| Tool call arguments | Each `teammate.tool` span | The arguments the model gave the call, as compact JSON, read from the call without changing it, so the tool runs with exactly what it was given. Strings are cut to 300 bytes (160 for fields that usually hold a body, such as a file’s `content`), objects to 24 fields and arrays to 24 items, 4 levels deep and 200 values in all; what’s left out is counted in place. Fields named like credentials (`password`, `apiKey`, `authorization`, `…token`, …), including percent-encoded names such as `api%5Fkey`, are replaced, maps of named values such as `env`, `buildArgs`, and `headers` keep only their names, and data URLs, encoded data, and binary values are summarized by their size. Getters, `toJSON`, and circular values are never followed. Dates, maps, sets, and binary values are measured with the engine’s own methods, never ones a value overrides, very large integers are summarized, and at most 1,024 keys of an object and 4,096 in a call are checked, inherited ones included, with the rest counted or marked unchecked. A proxy’s own code can still run when its arguments are read, and the limits count what is read rather than bound how long a proxy’s or the engine’s own code takes. Credential fields are recognized by their names, so a secret under an ordinary name is kept like any other value unless its text has a credential’s shape. Tool results are never recorded. |
| SQL statement | Each PostgreSQL query span | The statement’s shape, made from the whole statement as the query starts: keywords, identifiers, and `$1`, `$2`, … placeholders stay; string, numeric, and dollar-quoted literals become `?`, whatever their tag (`$$`, `$body$`, `$ü$`), comments are dropped, a quoted identifier is redacted for credentials as the name it spells, its doubled quotes undone, so `"password=""…"""` keeps only its name, and whitespace runs become one space. Parameter values are never collected (`enhancedDatabaseReporting` stays off), and nothing is added to the queries that run. A literal or comment the statement doesn’t close is cut there and marked. |

Previews are visible only to the record’s owner, for the retention period. They can hold private text the owner wrote or a model chose; redaction removes recognizable credentials, not ordinary text. OpenObserve also stores a normalized copy and fingerprint of each statement it receives (`o2_db_query_norm`), made from the shape, never from the statement that ran.

## Related traces and span age

A teammate turn, a background fork’s prompt, and a message a fork sends each start a trace of their own, linked to the work that started them. A trace’s details list its related traces, each opening as its own trace:

- **Started by**: the span another trace’s link names, such as the request that sent the message a turn answers.
- **Started**: the first span of each other trace whose links name this one, such as the turn a request started.
- **Same run**: other traces that recorded the same run ID, such as a request and its turn. A turn’s own span is stored only when the turn ends, so a running turn is found here by the first of its spans stored so far.

Relations come from what was recorded, never from timing. Links are read from what OpenObserve stores for each span, which records made before this change have too; run IDs were recorded already. Up to 10 traces of each kind are listed, and the page says when there are more. Spans are looked up by their exact trace and span ID pairs, and same-run traces are grouped by their stored owner and run, which the query requires again of each group before it orders and bounds them, and which are checked once more as each group is counted. So another owner’s records can’t crowd out or truncate the list, even if the owner condition on rows were lost; a backend that ignored both conditions could hide the owner’s own traces of a run, but not show another owner’s. A link to work that isn’t stored yet, has expired, or isn’t the owner’s is reported only as unavailable, without its IDs. Related traces are looked up with the trace, within 5 seconds; without them in time, the trace is shown alone and the page says so.

The Spans list can wait for spans to age: **Live** (the default) shows spans as soon as they are stored, **At least 1 minute old** and **Custom age** (1 to 60 minutes) leave out spans that started more recently, by the server’s clock, so the list shows work that has had time to finish. The range shown ends at that cutoff, newer-record checks use a fresh cutoff each time, and Refresh moves it forward. Recording is never delayed, Events are never affected, and an older span’s trace can still be filling in; a span’s age is no promise that its trace is complete.

## Access control

- The page reads `/v1/telemetry/status`, `/events`, `/events/:eventId`, `/spans`, and `/traces/:traceId`, all behind the same authentication as the rest of `/v1`. A trace’s related traces come with it, from queries that start with the owner’s condition, and only spans of the owner’s own traces are returned. The owner is always the verified caller: requests carry no owner, and every query Everything builds starts with the owner’s condition. Rows the backend returns are checked against the owner again before they’re shown. A trace or event of another owner answers exactly like one that doesn’t exist (404).
- Records are attributed when they are made, from verified identities and owned records: a request’s spans to its authenticated subject, including spans that began before authentication, and a teammate’s turns, prompts, and provider requests to the teammate’s owner. Unattributed records, such as unauthenticated requests and background warnings, are visible to nobody.
- Filters are validated against fixed patterns, and the query builder writes every value as an escaped SQL literal. OpenObserve’s SQL treats a backslash as an escape inside string literals, so doubling quotes alone isn’t enough; backslashes and control characters are refused both by the API schema and by the builder. There is no SQL, query, or admin passthrough.
- Apps a teammate shares act as their owner through the API, as they do for conversations, so they can read their owner’s telemetry too.

## Deployment

`services.openobserve` in [values.yaml](../helm/values.yaml) runs OpenObserve’s published image unchanged (`docker.io/openobserve/openobserve:v1.1.2`, pinned by digest, published for `linux/amd64` and `linux/arm64`; the same digest is on OpenObserve’s other registries), as one StatefulSet replica in local mode: SQLite metadata and Parquet files on its `openobserve-data` claim. It runs as user 1000 with a read-only root filesystem and no capabilities, has a ClusterIP Service on port 5080, and no Ingress.

| Setting | Default | Meaning |
| --- | --- | --- |
| `telemetry.retentionDays` | `7` | Days OpenObserve keeps (`ZO_COMPACT_DATA_RETENTION_DAYS`), and the range Everything’s API allows. 3 to 30. OpenObserve’s own default is 3650 days. |
| `telemetry.includeErrorText` | `true` | Record the redacted text of provider, SDK, and library error messages; `false` withholds it. It can quote prompts and other private text; see [Privacy and redaction](#privacy-and-redaction). |
| `telemetry.includeContent` | unset (follows `includeErrorText`) | Record [content previews](#content-previews): the message a turn answered, tool call arguments, and SQL statement shapes. `false` withholds them, `true` records them even with error text withheld. |
| `services.openobserve.enabled` | `true` | `false` removes the service; Everything’s `TELEMETRY_URL` is then empty, nothing is exported, and the page says telemetry is turned off. |
| `services.openobserve.volumes.data.persistentVolume.size` | `5Gi` | The disk; the installer asks for it like the others. |
| `services.openobserve.resources` | requests 50m CPU, 128Mi; limits 1 CPU, 768Mi | See [Resources](#resources). |

Everything’s settings come from the chart: `TELEMETRY_URL` (the Service, or empty), `TELEMETRY_USERNAME`, `TELEMETRY_PASSWORD_FILE`, `TELEMETRY_RETENTION_DAYS`, `TELEMETRY_INCLUDE_ERROR_TEXT` (`true`, the default, or `false`), `TELEMETRY_INCLUDE_CONTENT` (`true` or `false`; unset, it follows `TELEMETRY_INCLUDE_ERROR_TEXT`), `TELEMETRY_SERVICE_VERSION`, and optionally `TELEMETRY_READ_SAMPLE_RATIO` (0–1) and `TELEMETRY_TIMEOUT_MS`. Malformed settings or an unreadable password file never stop Everything from starting; the page reports telemetry as unavailable, and nothing is recorded.

**Upgrades and the new defaults.** Upgrades from Settings run `helm upgrade --reset-values` with the new chart’s values, its `values.prod.yaml`, and the installer’s saved settings file, and the installer layers the same files. An installation whose settings file never set `telemetry.includeErrorText` therefore records error text and content after upgrading to this version; one whose settings file sets it to `false` keeps both withheld, unless it also sets `telemetry.includeContent: true`. Values passed to an earlier Helm release by hand, but not saved in the settings file, aren’t carried over by these upgrades.

**Credentials.** `templates/telemetry-credentials.yaml` derives OpenObserve’s root password from a purpose label and the session encryption key, as the Fleet gateway’s session key is, so no new install-time value is needed. OpenObserve reads it as `ZO_ROOT_USER_PASSWORD`; Everything mounts it as a file, so it is never in the environment fleetd and its commands inherit. Neither the browser nor teammate pods receive it. OpenObserve keeps the password it was first started with, so changing the session encryption key, which the installation treats as a stable master key, leaves the Secret and OpenObserve’s account disagreeing. With this chart, the recovery is to delete the `openobserve-data` claim, losing telemetry history, so OpenObserve starts over with the new password. That is a tradeoff of deriving the password from the key, not a limit of OpenObserve: giving OpenObserve its own persisted credential would avoid it, and isn’t done yet. Pods in the release namespace, including teammate pods, can reach the Service, but every data endpoint requires that password.

**No outside connections.** By default OpenObserve reports usage to its makers and downloads GeoIP databases, LLM prices, and redaction patterns from the internet, even with `ZO_TELEMETRY=false`. The chart turns all of them off (`ZO_TELEMETRY`, `ZO_MMDB_DISABLE_DOWNLOAD`, `ZO_MODEL_PRICING_ENABLED`, `ZO_REGEX_PATTERNS_SOURCE_URL`), along with its web UI, API documentation, MCP server, metrics endpoint, and query history. Observed over a 30-second start in its network namespace: the defaults connected to `raw.githubusercontent.com` and `geoip.zinclabs.dev`; the chart’s settings made no outside connections.

## Reliability and limits

- Export is asynchronous and bounded: spans and events wait in fixed queues (2048 spans, 1024 events) and are sent in batches every 2 s and 1 s over OTLP/HTTP with a 10 s deadline and the exporters’ backoff for retryable statuses. A slow or unreachable OpenObserve never delays or fails chat, provider calls, or requests; when the queues are full, further records are dropped and counted. Failed and dropped batches are reported on the page and by one line on standard error when exports start failing and when they recover.
- Shutdown flushes what is queued, within the export deadline. A crash, out-of-memory kill, or node loss loses what was still queued in Everything’s memory. OpenObserve writes received records to its write-ahead log on its disk; records survive its restarts (tested), but this is a single node without replication or backups.
- Retention is deletion by OpenObserve’s compactor: data older than `retentionDays` is removed within a few hours of expiring, not at the exact moment. Disk use depends on volume; there is no disk-based cap, so size the claim for your load and watch it.
- Content previews make spans that carry them larger: a turn, tool, or query span can hold up to 2,000 more bytes, and OpenObserve keeps a normalized copy of each statement too. Only those spans grow; prompts, provider requests, and requests to Everything don’t. Through the export pipeline, a synthetic turn with a short message, three tool calls, and two queries came to about 485 bytes of attributes a span with content withheld and about 695 with it recorded, and about 1,100 with oversized inputs. In one disposable OpenObserve, 16,000 such repetitive synthetic spans took about 611 KB of write-ahead log with content and 378 KB without, before compaction. These are limited synthetic figures, not a measure of real use, compression, or capacity: the default 5Gi claim can fill sooner with content recorded, so watch it, and enlarge it or withhold content if needed. Nothing resizes it automatically, and seven days of retention is a configured horizon, not a guarantee that the disk holds a week.
- Spans are kept for every non-read request and for reads that fail or are slow; events are never sampled. The page’s own reads are queried with tracing suppressed.
- Records arrive in batches as work finishes, so a trace can be incomplete when it’s first opened. While **Watch for new records** is on, an open trace whose root span hasn’t arrived is checked every 5 seconds, for up to 10 minutes after the record. **Refresh** reloads the list from its newest page, even for an unchanged custom range, and reloads the open record and its trace, which stay open; older pages load again on request. A trace that can’t be loaded says so and offers **Try again**.

## Resources

OpenObserve’s sample Kubernetes manifest (requests 256m CPU and 50Mi, limits 4 CPU and 2Gi) is an example, not a measured minimum, and its defaults size caches and memory tables as a share of the node. The chart bounds them (`ZO_MEMORY_CACHE_MAX_SIZE` 64 MB, `ZO_MEMORY_CACHE_DATAFUSION_MAX_SIZE` 128 MB, `ZO_MEM_TABLE_MAX_SIZE` 64 MB, `ZO_MAX_FILE_SIZE_IN_MEMORY` 16 MB) and sets requests of 50m CPU and 128Mi, and limits of 1 CPU and 768Mi.

Measured on 2026-10-23 with OpenObserve v1.1.2 (amd64) in Docker, limited to 1 CPU and 768 MiB, with every setting the chart renders. The workload went through Everything’s own export pipeline: about five request traces a second, each with two PostgreSQL spans; a teammate turn every two seconds, with its prompt, three tool calls, and a provider request; and a model failure with its turn failure every ten seconds. After ingesting, 300 owner-scoped API queries ran (event pages, span searches, and trace lookups for three owners). Memory is Docker’s reported usage, sampled about every two seconds.

| Phase | Peak memory |
| --- | --- |
| Idle, first minute | 29 MiB |
| Ingesting for three minutes (897 request traces, 90 turns) | 39 MiB |
| 300 queries | 97 MiB |
| Afterwards, caches warm | 81 MiB |

Nothing was dropped, the container was never killed, and it used 6.6 MB of disk. A second run ingested the same mix for 15 minutes (4,485 request traces, about 450 turns, 16,000 spans, and 180 events): memory peaked at 73 MiB while ingesting and 131 MiB while searching, and settled at 95 MiB; the data took about 4.5 MB beyond OpenObserve’s 5.8 MB metadata database, roughly 300 bytes a span. `pnpm test:telemetry --browser`, which also restarts OpenObserve and replays its write-ahead log, peaked at 266 MiB. In the measurement runs the data was still in OpenObserve’s write-ahead and pending files, so moving it into long-term storage and compacting it, which happen later, were not measured. At that rate 5Gi holds on the order of 15 million spans, a week of about 25 spans a second, far more than one installation’s requests and teammate work produce once the browser’s polling is sampled. With OpenObserve’s defaults (still limited to 1 CPU), the same workload peaked at 245 MiB with unbounded caches and the GeoIP databases it downloads loaded; on a larger node, its defaults grow further. These are low-volume measurements on one machine, not a sizing guarantee: memory grows with concurrent searches, wide time ranges, and compaction of larger files, and disk grows with volume. The browser’s polling adds little, since quick successful reads are sampled at 5%.

## Operator access

OpenObserve is reachable only inside the cluster. To inspect it directly, for example for unowned background warnings:

```sh
kubectl -n <namespace> port-forward statefulset/openobserve 5080:5080
kubectl -n <namespace> get secret telemetry-credentials -o jsonpath='{.data.password}' | base64 -d
# Basic auth as everything@telemetry.local; stream "everything", types logs and traces.
curl -u "everything@telemetry.local:$PASSWORD" -H 'content-type: application/json' \
  'http://127.0.0.1:5080/api/default/_search?type=logs' \
  -d '{"query":{"sql":"SELECT * FROM \"everything\" ORDER BY _timestamp DESC","start_time":…,"end_time":…,"from":0,"size":50}}'
```

The web UI is turned off; set `ZO_UI_ENABLED` to `"true"` in a values override to use it through the port-forward.
